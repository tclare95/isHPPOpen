## #71 handoff / collection ownership

#71 publishes a verified, versioned outfall catalogue in small private S3 snapshots, and deterministic per-environment named selection plans. #72 **consumes** the resolved plan (including provenance, catalogue age, configured-set memberships and unresolved IDs); it does not own refresh, remapping, provider-wide discovery or an implicit fallback when no selection exists. Poll only the deduplicated eligible IDs. Disabling selection stops future polls without erasing earlier evidence or event history.

Plan to batch/constrain provider requests and isolate per-outfall errors. The previous 15-minute rhythm is a *candidate* initial operating interval, not current permission to enable a schedule. A roughly 30-minute freshness threshold is provisional until source timestamps and publication lag are demonstrated; provider-specific policy must distinguish source age from successful fetch age. A valid 200 response can still contain an ArcGIS `error`, duplicate IDs, inconsistent fields or stale information. Keep a bounded run summary for attempted/fetched/unchanged/persisted/failed and last verified success, without raw body logs.

## Separate model: evidence, current status, spill event

**Source evidence / source claim.** Retain the provider/source and original asset IDs, source/report timestamps (with semantics and whether verified), fetched time, relevant status/event boundaries, payload checksum/opaque evidence reference, source schema, selection/collection-run reference and validation/reconciliation outcome. The evidence is immutable; repeating identical substantive provider data does not require creating a new logical claim. Still retain run heartbeats and ingestion health. Distinguish provider-origin event IDs, if any, from provider outfall IDs and transient ArcGIS row IDs.

**Current monitor projection.** `reportedState` (`spilling | not_spilling | offline | unknown`), last source statement time, last successful fetch/persist time, `freshness` (`fresh | stale | unknown`), and `effectiveState` (`spilling | not_spilling | unknown`). A previously reported active state may remain visible while effective state is unknown. The effective status is a confidence-limited present-tense projection; it does **not** close an event. If a fresh source reports stopped without a verified event end, the reported/effective current state can advance while the event remains open/unresolved pending boundary evidence.

**Spill event.** Stable internally assigned `eventId` and canonical provider/outfall identity, optional provider event ID, authoritative reported start/end when verified, uncertain bounds when not verified, `lifecycle` (`ongoing | completed | unresolved`), identity/reconciliation state, source claim links and immutable material revisions (including superseded values and reason). A completed interval can be first discovered in one later poll, including `LatestEventStart` and `LatestEventEnd` when `Status` currently says not spilling. Distinguish *a provider statement about the latest event* from *proof that all intervening spills were reported*: a lost/overwritten latest event cannot be reconstructed without evidence.

Do not treat `LastUpdated` as a trusted global monotonic revision number until provider semantics have been verified. Receipt order is also not automatically a reliable source-correction order. Prefer explicit provider event IDs/revisions when evidenced; otherwise use stable claim lineage and deterministic, conservatively ordered reconciliation. If authoritative precedence is inconclusive, preserve competing claims and hold a disputed projection rather than choose whichever worker commits last. Exact outfall identity changes are governed by #71's reviewed mapping.

## Identity, corrections and concurrency

An internal ID is created once for a *reasonably unambiguous discharge*, never derived solely from a mutable start timestamp. Bind provider claims (or a trustworthy provider event ID if available) to canonical event identity in a durable, conditional way; duplicate collectors must converge on one ID. Two separate legitimate discharges close in time must not be merged using fuzzy temporal proximity. If a corrected start/end could refer to either of two events, retain both and record an unresolved claim requiring reviewed reconciliation; no admin UI is needed in this slice.

Corrections to ongoing, already completed or archived events create a new **material** revision under the original ID. Duplicate claims do not create revisions. Both the event's query placement and completion/expiry eligibility must follow the authoritative revision. A correction that clears `endedAt` or makes completion uncertain prevents expiry. An authoritative new completion of a previously unresolved event may allow future eligibility only after verified archival.

The implementing agent may use per-asset serialisation, conditional projection writes with bounded retries, or another appropriately simple technique, but acceptance must prove **no forked event identities, lost claims, lost revision order or stale reversion** under concurrent retries. Treat identity linking, event head and relevant query-index updates as one logically recoverable change, not unrelated best-effort writes. If a conflict cannot safely be resolved, keep a non-final reconciliable state.

## Persistence and recovery

Recommended practical sequence:

1. Validate the selection and source response; derive an idempotent semantic claim identity that does not depend on transient poll/run timestamps. Retain run outcome separately.
2. Write the immutable original/normalised evidence and required revision payload to private CSO S3 objects, validate checksum/readback and establish committed references/generation. Never overwrite old versions.
3. Conditionally project the authoritative current monitor state, event head, identity links and bounded query indexes in CSO-specific DynamoDB structures. Only acknowledge durable success when archive/evidence and projections agree.
4. On partial failure, make the incomplete commit diagnosable and replayable. S3 failure leaves the old state unchanged; S3 success followed by Dynamo failure must converge on retry. Duplicate retries should be no-ops. Do not advance authoritative source checkpoints past uncommitted evidence.

This describes invariants, **not** a mandate to reproduce the observation manifest format, build distributed transactions, create a general event-sourcing framework or add an SQS bus. RDP already shows useful verified S3 generation/conditional-write patterns. Its observation-specific archive compaction and two-date fetched-at precedence do not automatically make suitable CSO policies. Bounded replay needs a discoverable recovery marker/reference, not merely an orphaned S3 object no one can find.

## Retention, indexing and archive read consistency

- Maintain logical current-state, event head/identity, bounded event-by-outfall/time overlap query, and source health views independently. It is an implementation decision whether some CSO views share one **CSO-owned** table. **Never** fold CSO event heads into the existing scalar gauge `Observation` data model, partitions or 365-day TTL.
- Authoritative completed events remain hot for **24 UTC calendar months from the verified `endedAt`**, not from first-seen/start time, fetched time or the ingestion date. Define month arithmetic in UTC with an explicit end-of-month/leap-day rule and test it. Open/unresolved rows and necessary discoverability indexes have no TTL.
- Before any expiry attribute is assigned, verify current canonical event/version, links to required revision and source evidence, manifest checksum/count/generation and direct private S3 Standard read path. Keep previously verified hot rows on failure. New CSO event archives must remain directly GetObject-readable after the cutoff; the legacy 3-month snapshot archive/Glacier policy does not govern them. No automatic evidence/revision deletion until a separately approved policy.
- A late correction to a previously archived event must commit a new canonical generation, revise the event head/identity timeline and make the corrected event discoverable where its new interval belongs. If reopened/unresolved, make it non-expiring and hot-discoverable before acknowledging the revision; do not mint a second event.
- **Logical cutoff vs physical TTL:** Dynamo TTL is asynchronous and may leave overlap. A completed event starting before the cutoff but ending recently, or a three-year-old open spill, may still be hot. The query must resolve relevant carry-in intervals, not naively route by `startedAt` or partition month alone. Deduplicate by stable event ID and validated authoritative revision, never by start timestamp.
- Use bounded per-outfall/time indexes and committed archive manifests (or equivalent bounded location/interval lookup), not Dynamo `Scan` or unbounded S3 listing/history reconstruction. A first-party read can return verified available events with honest coverage even where other periods have no proven completeness. An **expected committed** missing/corrupt object is integrity failure, not an unknown coverage interval.
- Preserve query paging semantics under archive generation or physical TTL movement, with a stable view or explicit stale cursor. RDP's 30-minute authenticated/encrypted cursor, 20s handler work limit and 4MiB response budget are good defaults, but exact cursor implementation need not be copied.

## API deployment choice: extend the existing read host

**Decision for v1: extend the implemented `RiverDataPlatform.ReadApi` Lambda and existing HTTP API stage**, adding separate CSO read services/DTOs and six explicit routes described in [api-contract.md](api-contract.md). Do **not** create a separate CSO API Gateway or separately deployed CSO read Lambda at the outset.

Rationale: the current host already handles exact stage/account/role validation, single first-party OIDC/SigV4 trust boundary, API/error envelopes, cursors, query and response budgets, stage-specific manual deployment and signed smoke. It is one low-traffic internal client, and a new deployable would duplicate IAM/bootstrap/release/testing surface without a demonstrated runtime isolation requirement. CSO code remains a domain module, **not** a `MeasurementRegistry` extension. Read services receive read-only CSO storage interfaces, and collection/write dependencies are not registered.

**Acknowledged trade-off:** one Lambda execution role necessarily has the union of observation and CSO **read** privileges, so this is *resource-scoped least privilege*, not distinct execution-role isolation. Grant separate narrowly bounded CSO GetItem/Query and private GetObject/GetObjectVersion resources (plus the tightly justified bucket-level missing-key-diagnostic exception if needed), without granting any CSO writes or wildcard archive access. Keep collector IAM separately scoped. If future compliance, high-volume queries or independent failure limits require role-level separation, a second handler behind the *same* API can be introduced later without changing product routes.

Six explicit `GET` routes: `/v1/cso/outfalls`, `/v1/cso/outfalls/status`, `/v1/cso/outfalls/{id}/events`, `/v1/cso/events/{eventId}`, `/v1/cso/events/{eventId}/revisions`, `/v1/cso/outfalls/{id}/health`. The outfall catalogue derives from #71's **verified** snapshot and has no implied impact/proximity claim. Bind IDs consistently to the provider+asset identity; don't leak object keys or accept arbitrary S3 paths.

**Concrete IAM/deployment integration points to revisit:** `template.yaml` creates only measurement route keys and its Lambda `ReadPermission.SourceArn` matches `/v1/measurements*`; `deploy/read_api_iam.py` builds an exact invoke allowlist plus deny outside it; the read execution policy and `deploy/bootstrap.py` boundary constrain Dynamo/S3 to observation resources; `RiverDataPlatform.ReadApi.Function` hard-codes permitted route keys in validation/logging. All must be extended together, with wrong-stage/unsigned denial tests. Do not change the original four routes, replace the cursor secret or silently expand to `execute-api:*/*`.

## Safety and release posture

RDP has isolated staging/production stacks, IAM boundaries and manual prepare/review/apply; production currently runs the observation pattern independently. The CSO slice must have **separate runtime/activation approval** and must not ride on existing `CollectorsEnabled` or `ScheduleEnabled` gauge flags. Staging is a tiny, mostly idle environment with a few explicit selected assets and fixture-created old events; no two-year stage replica, continuously scheduled CSO poll or live source probe just to merge documentation. First-party website read migration, alert compatibility and eventual legacy retirement are separate changes.

Known open technical evidence: current live ArcGIS status code/domain, actual timestamp meaning and monotonicity, availability and stability of provider event IDs, whether older events are revised retroactively, provider query limits/publication lag, and precise operational freshness threshold. Validate these using approved, bounded read-only source fixtures before fixing provider-specific assumptions in code. Do not pretend this repo review verified live data.
